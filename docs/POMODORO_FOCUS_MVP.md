초안은 진입점을 홈의 40dp 아이콘 하나로 두고 알림을 통째로 제외했었다. 그 조합은 "메뉴에 항목 하나 추가"와 같고, 문서 스스로 그것이 목표 잠금 30명 / 부모 모드 15명의 경로라고 적어 두었다. 이 개정판은 그 모순을 닫는다.

이 문서는 **뽀모도로 집중 세션**의 제품/도메인/analytics/QA/배포 경계 계약을 고정한다.

이 기능은 `docs/RETENTION_DIAGNOSIS_2026_08.md`의 단계 1·2와 **다른 종류의 베팅**이다. 단계 1이 이미 있는 사용자를 넛지로 붙잡는 리텐션 패치라면, 이것은 앱을 여는 이유 자체를 새로 만드는 카테고리 베팅이다. 따라서 판정 지표와 배포 순서를 단계 1과 분리해서 관리한다. 이 구분을 잃고 "리텐션 개선 기능" 하나로 묶으면 성공/실패 판독이 불가능해진다.

## 한 줄 목표

사용자가 앱을 열어 `집중 25분 → 휴식 5분` 사이클을 돌리고, **그 사이클 전 구간에서 방해 앱이 실제로 차단되며**, 오늘 몇 번 집중했는지가 남게 한다.

## 제품 의도

### 왜 지금 이 기능인가

`docs/RETENTION_DIAGNOSIS_2026_08.md` 2.3이 "재방문 트리거가 0개"라고 진단했다. 그런데 `block_source` 분해를 보면 차단 가치의 60.0%(`routine` 14,450 / 24,070)를 루틴이 만든다. **루틴은 차단을 만들지만 앱을 열 이유를 만들지 않는다.** 한 번 설정하면 배경에서 조용히 돈다.

그래서 단계 1의 세 항목이 전부 *바깥에서 안으로 부르는* 구조다 — 아침 알림, 홈 상단 카드, 수정 유도. 뽀모도로는 반대로 **사용자가 스스로 앱을 여는 것에서 시작**한다. 공부를 시작할 때 열고, 4사이클이면 하루에 네 번 연다.

같은 문서 4장이 남긴 비대칭도 같은 방향을 가리킨다.

| 차단 화면에서의 선택 | D7 | D14 |
| --- | ---: | ---: |
| 순응 (`first_core_action_completed`) | `27/281 = 9.6%` | `15/215 = 7.0%` |
| 우회 (`emergency_unlock_used`) | `68/236 = 28.8%` | `44/181 = 24.3%` |

4장이 명시한 대로 이 수치는 인과로 읽으면 안 된다(반복 이벤트 코호트에 기존 유저가 섞인다). 다만 방향만 취하면 **앱 안에서 무언가를 하는 사람이 남는다**이고, 뽀모도로는 정확히 그 행동을 매일 만드는 장치다.

### 가장 큰 리스크 — 새 모드의 기저율

이 앱에서 "새 모드"를 만들었을 때의 실측치가 이미 두 개 있다.

| 기능 | `block_source` users |
| --- | ---: |
| 목표 잠금 | 30 |
| 부모 모드 | 15 |

`docs/RETENTION_DIAGNOSIS_2026_08.md` 3장이 "신규 기능 확장"을 "지금 하지 않는 것"에 넣은 근거가 이 두 숫자다. **뽀모도로가 왜 다를 것인지에 대한 답이 없으면 이 문서를 실행으로 옮기지 않는다.**

현재 가진 답은 하나뿐이다. 목표 잠금과 부모 모드는 *기존 사용자의 기존 의도*를 깊게 판 기능이고, 뽀모도로는 *다른 의도를 가진 다른 사용자*를 데려온다. 그렇다면 결론이 하나 따라온다 — **메뉴에 항목 하나 추가하는 방식으로 출시하면 반드시 30명이 된다.** 스토어 등록정보·스크린샷·키워드까지 포지셔닝을 함께 바꿔야 효과가 나온다. 이건 코드 범위 밖이고 되돌리기 어려우므로 아래 "결정 대기 항목"에서 별도로 다룬다.

유입이 `google-play organic 540 / direct 65 / google organic 1`로 사실상 100% 오가닉이라, 리뷰 프롬프트(단계 0) 말고 남은 성장 레버가 카테고리 확장뿐이라는 점이 이 베팅의 배경이다.

## 스토어 포지셔닝 계약

기저율(목표 잠금 30명 / 부모 모드 15명)을 벗어나는 유일한 경로다. 코드가 아니라 유입을 바꾸는 작업이므로 **구현과 별개의 완료 조건**으로 관리한다.

유입은 `google-play organic 540 / direct 65 / google organic 1`로 사실상 100% 오가닉이다. 리뷰 프롬프트(단계 0)를 빼면 남은 성장 레버가 카테고리 확장뿐이라는 것이 이 결정의 근거다.

| 항목 | 내용 | 경계 |
| --- | --- | --- |
| 앱 이름 / 짧은 설명 | 차단 정체성을 유지한 채 집중 세션을 병기한다. 차단을 빼고 뽀모도로 앱으로 바꾸지 않는다 | Play Console manual |
| 스크린샷 | 집중 화면과 휴식 화면을 상위 3장 안에 넣는다. 휴식 중에도 차단이 유지된다는 점이 스크린샷 카피에서 읽혀야 한다 | Play Console manual |
| 키워드 | 뽀모도로 / 포모도로 / 집중 타이머 계열 | `docs/PLAY_STORE_ASO.md`의 attribution gate를 따른다 |
| 온보딩 | 뽀모도로로 유입된 사용자가 앱 차단 전용 온보딩만 만나지 않게 한다 | **MVP 밖.** 아래 참고 |

### 온보딩 분기는 MVP에 넣지 않는다

뽀모도로 검색으로 들어온 사용자는 앱 차단용으로 만들어진 온보딩을 만난다. 이건 실재하는 구멍이지만 지금 건드리지 않는다.

- `onboarding_step_complete`가 `503 / 525 = 95.8%`로 퍼널 중 가장 건강하다. 손댈 때의 하방이 크다.
- `onboarding_experiment_exposed` 510명으로 **A/B가 진행 중**이다. 여기에 분기를 얹으면 두 실험이 섞인다.

따라서 온보딩은 진행 중인 A/B가 닫힌 뒤 별도 판단으로 분리한다. 스토어에서 넘어온 사용자의 첫인상은 MVP 구간에서는 스크린샷과 홈 진입점이 감당한다.

### 판정

포지셔닝 변경의 성과는 기능 채택률이 아니라 유입으로 본다. 아래 "측정 계획 / 30일 확인"의 `newUsers` 추이와 Play Console 리스팅 지표가 그 축이다. 스토어를 바꾸지 않은 채 채택률만 낮게 나온 결과를 "수요 없음"으로 읽지 않는다.

## 세션 진행 알림 계약

**초안의 오류를 고친 항목이다.** 초안은 "뽀모도로 리마인더 알림"을 단계 1과의 지면 충돌을 이유로 제외했는데, 그 제외가 기능을 작동 불능으로 만든다. 사용자는 공부하려고 화면을 끄고 폰을 엎어둔다. 25분이 끝나 휴식이 시작돼도 알 방법이 없으면 사이클이 성립하지 않는다.

두 가지는 다른 것이다.

| 종류 | 예 | 판단 |
| --- | --- | --- |
| **리마인더 알림** | "어제 루틴이 N번 막았어요" — 앱 밖에서 사용자를 불러들인다 | 단계 1의 신규 채널과 같은 지면. **계속 제외** |
| **세션 진행 알림** | 현재 페이즈와 남은 시간을 세션 내내 띄우는 상시 알림 | 긴급해제 카운트다운과 같은 부류. **MVP에 포함** |

계약:

- 포그라운드 서비스가 세션 수명 동안 상시 알림을 유지한다. 세션이 끝나면 알림도 사라진다.
- 알림은 현재 페이즈(집중/휴식), 남은 시간, 사이클 위치를 보여준다.
- 페이즈가 바뀌는 순간에만 알림을 갱신해 소리/진동을 낸다. 초 단위 갱신은 무음으로 한다.
- 전용 채널을 신설한다. `ROUTINE_CHANNEL_ID`를 재사용하지 않는다 — 사용자가 루틴 알림을 끄면 세션 알림까지 사라지고, 그 반대도 마찬가지다.
- 채널 importance는 `DEFAULT`. 페이즈 전환은 알려야 하지만 heads-up으로 화면을 덮을 일은 아니다.
- 알림 권한이 없거나 채널이 꺼져 있어도 **세션과 차단은 그대로 동작한다.** 알림은 편의이지 잠금의 전제가 아니다.

`KeepDnsVpnService`가 `FOREGROUND_SERVICE_SPECIAL_USE`로 이미 같은 패턴을 쓰고 있고 권한도 선언되어 있으므로 새 영역이 아니다.

## MVP 범위

### 포함

1. **사이클 길이** — 프리셋 `25/5`, `50/10` 과 사용자가 직접 정하는 커스텀. 4번째 집중 후 긴 휴식(프리셋은 각각 15분 / 20분). 아래 "사이클 길이 계약".
2. **세션 실행과 복원** — 페이즈(집중/짧은 휴식/긴 휴식), 사이클 인덱스, 페이즈 만료 시각을 저장하고 앱이 죽거나 재부팅돼도 벽시계 기준으로 복원한다.
3. **사이클 전 구간 차단 연속성** — 아래 "차단 판단 정책"의 핵심 계약. 휴식 중에도 차단을 풀지 않는다.
4. **앱 내 휴식 화면** — 남은 휴식 시간, 다음 사이클 번호, 지금 종료 진입점.
5. **오늘 완료 사이클 수** — 세션 화면과 종료 화면에서 확인. 별도 통계 지면은 만들지 않는다.
6. **언제든 종료** — 확인 1회, 비난 없는 톤.
7. **차단 앱 선택 재사용** — 기존 앱 선택 도메인/UI를 그대로 쓴다. 뽀모도로 전용 앱 목록을 새로 만들지 않는다.
8. **세션 진행 알림** — 포그라운드 서비스가 현재 페이즈와 남은 시간을 세션 내내 띄운다. 위 "세션 진행 알림 계약".
9. **analytics 계약** — 아래 표.

| 태스크/할 일 목록 연동 | 차단 정체성 밖이고, 사용자 입력 문구가 analytics·공유 privacy 경계를 넓힌다 |

## 사이클 길이 계약

초안은 커스텀 길이를 "2차 후보"로 제외했다. **그 판단은 포지셔닝을 바꾸기 전의 것이다.** 기존
사용자 대상 실험이라면 프리셋 2종으로 채택률만 보는 게 맞지만, 이 기능은 뽀모도로 카테고리에서
사용자를 데려오는 베팅이 됐고 그 카테고리에서 길이 조절은 기본 사양이다.

`preset` 파라미터가 아직 GA4 에 등록되기 전이라는 점도 지금 넣는 근거다. 배포 후에 스키마를
바꾸면 배포 전후 데이터가 같은 축에서 안 읽힌다.

### 저장 형태

**길이는 프리셋 key 가 아니라 분 값으로 저장한다.** key 만 저장해 두고 읽을 때 표에서 찾으면,
프리셋 정의를 나중에 손봤을 때 이미 돌고 있던 세션의 남은 시간이 소급해서 달라진다. 커스텀은
애초에 표에 없다.

| 저장 key | 의미 |
| --- | --- |
| `pomodoro_preset` | `25_5` / `50_10` / `custom` — 라벨과 analytics enum |
| `pomodoro_focus_minutes` | 집중 길이(분) |
| `pomodoro_short_break_minutes` | 짧은 휴식 길이(분) |
| `pomodoro_long_break_minutes` | 긴 휴식 길이(분) |

### 허용 범위

| 값 | 범위 | 이유 |
| --- | --- | --- |
| 집중 | 5–120분 | 상한이 없으면 집중 세션이 목표 잠금 흉내를 낸다. 기간 기반 장기 잠금은 `docs/GOAL_LOCK_MVP.md` 가 할 일이다 |
| 짧은 휴식 | 1–60분 | — |
| 긴 휴식 | 1–120분 | — |
| **반복 횟수** | **2–8회** | 집중 1회는 사이클이 아니다 — 반복 없는 한 번의 잠금은 타이머 세그먼트가 하는 일이다 |

**반복 횟수가 총 잠금 시간을 가장 크게 흔든다.** 4회로 고정돼 있던 동안 `25/5` 를 고르면 무조건
2시간 10분, `50/10` 이면 4시간 10분이었고 사용자가 "1시간만 집중"을 만들 길이 없었다. AppBlock 도
work/break 와 함께 **사이클 수**를 조절하게 한다.

횟수는 길이와 같은 이유로 세션에 값으로 저장된다. 따라잡기 루프의 상한도 상수가 아니라 세션의
횟수를 따라간다 — 8회 세션이 4회에서 멈추면 안 된다.

범위를 벗어난 값은 **세션을 만들지 않는다.** 저장된 값이 범위를 벗어난 채 발견되면 세션 없음으로
읽는다 — 손상된 값이 사용자가 예약한 적 없는 길이의 잠금이 되는 경로를 막는다.

### analytics

`preset` 이 `custom` 이면 그 값만으로는 길이를 알 수 없다. `pomodoro_session_started` 에
`focus_minutes_bucket` 을 추가해 길이 신호를 남긴다. **원본 분 값은 보내지 않는다.**

경계는 두 프리셋이 서로 다른 칸에 떨어지도록 잡았다 — 25분은 `25_34`, 50분은 `50_plus`.
프리셋과 커스텀 분포를 같은 축에서 비교할 수 있어야 커스텀이 실제로 쓰이는지 읽힌다.

- `focus_minutes_bucket`: `0_14`, `15_24`, `25_34`, `35_49`, `50_plus`
- `cycle_count_bucket`: `2`, `3`, `4`, `5_6`, `7_plus`

### 입력 UI

프리셋 두 장 아래에 `직접 설정` 카드를 한 장 더 둔다. **별도 화면을 만들지 않는다** — 고른
카드 안에서 바로 길이를 조절해 선택과 조절이 같은 자리에 있게 한다.

길이 입력은 목표 잠금의 커스텀 기간이 쓰는 `SetupStepper` 를 그대로 쓴다. 같은 성격의 입력이
앱 안에서 두 가지 모양을 갖지 않게 한다.

**스테퍼는 5분 단위로 움직인다.** 도메인은 1분 단위까지 허용하지만, 25분에서 50분까지 25번
눌러야 하는 입력은 쓰이지 않는다. 짧은 휴식의 하한 1분은 스테퍼로 도달할 수 없고 5분이 실질
하한이다 — 도메인은 관대하게, 화면은 의견을 갖게 둔 것이다.

## 잠금 계층 합류 계약

**초안의 가장 큰 구조적 실수를 고친 항목이다.** 초안은 뽀모도로를 `AnalyticsBlockSource` 의 여섯
번째 값, 즉 루틴·목표 잠금·부모 모드와 나란한 **여섯 번째 잠금 모드**로 만들었다. 그 결과 기존
잠금 계층에서 통째로 빠져 있었다.

| 항목 | 초안 상태 | 결과 |
| --- | --- | --- |
| `LockHistoryRecorder` | 호출 안 함 | 2시간짜리 세션이 잠금 기록에 안 남았다. 성과 리포트(#465)·주간 요약(#211)에도 안 잡힌다 |
| `lock_session_start` / `_end` | 미발생 | `docs/RETENTION_DIAGNOSIS_2026_08.md` 의 세션 완주율 `79/2,054` 분모에 안 들어갔다 |
| 리뷰 프롬프트 | 무장 안 됨 | 단계 0이 리뷰를 성장 엔진으로 살리는 중인데 집중 세션 완주는 기여하지 않았다 |
| `first_lock_configured` | 미기록 | 뽀모도로로 첫 잠금을 건 사용자가 활성화 퍼널에서 통째로 안 보였다 |
| `TimedLockSessionController` | 옆에 하나 더 만듦 | 같은 일을 하는 컨트롤러가 둘이 됐다 |

### 왜 합칠 수 있는가

**휴식 중에도 차단을 유지하기로 한 결정 때문에, 집중 세션은 이미 "연속된 타이머 잠금 하나"다.**
잠금 관점에서 둘은 같다 — 시작 시각이 있고, 끝나는 시각이 있고, 그 사이 내내 막힌다. 다른 것은
그 시간 동안 앱이 무엇을 보여주느냐뿐이고, 페이즈는 잠금이 아니라 그 위에 얹힌 표현·알림 레이어다.

그래서 통합이 배선이 아니라 구조가 된다. 기록·지표·리뷰를 하나씩 복제해 붙이는 것이 아니라,
세션이 타이머 잠금이 되면 **전부 따라온다.**

### 계약

- 세션 시작은 `TimedLockStarter.start(origin = TimedLockStartOrigin.Pomodoro)` 를 거친다.
  예약 길이는 집중 하나가 아니라 **사이클 전체**다 (`Focus25` → 130분).
- `PomodoroSessionController` 는 잠금을 스스로 만들지 않는다. 페이즈 전환과 페이즈 계측만 한다.
- 잠금을 세우지 못하면(이미 다른 타이머 잠금이 활성, 막을 대상 없음) **세션도 시작하지 않는다.**
  화면만 집중 중이라고 말하고 실제 잠금은 다른 것이 쥐고 있는 상태를 만들지 않는다.
- 세션이 끝나면(완주·조기 종료 모두) `LOCK_TIME` 을 내리고 잠금 기록을 남긴다. 기록 구간은
  예약 길이가 아니라 **실제로 잠겨 있던 시간**이다.
- `block_source = pomodoro` 는 유지한다. 차단 건수는 여전히 분리해서 봐야 한다. 차단 판정에서
  `isShouldPomodoroBlock` 이 `isLockTime` 보다 앞에 있으므로 출처가 `timed_lock` 으로 흡수되지 않는다.
- 새 상수: `AnalyticsScheduleType.POMODORO`, `AnalyticsSource.HOME_POMODORO`.

### 런타임 증적 (실기기 SM-G991N, 2026-08-31)

- 세션 시작 → `pomodoro_started_at = 15:45:17`, `lock_time = 17:55:17`. **정확히 2시간 10분**,
  즉 사이클 전체 길이의 타이머 잠금이 실제로 생성됐다.
- 세션 종료 → `lock_time` 삭제, `long_block_time` / `total_block_time` 기록.
- `잠금 기록` 화면에 `잠금 횟수 1회`. Room 원장에 들어갔다.

### 진입점도 합친다

홈의 전용 40dp 아이콘을 없앴다. 집중 세션은 타이머 시트의 **세 번째 세그먼트**(`카운트다운 /
타이머 / 사이클`)로 들어간다. 사용자 모델이 하나가 된다 — *"잠금 시간을 정한다 → 한 번이냐
반복이냐"*.

시트에는 이미 두 모드를 고르는 세그먼트가 있었다. 집중 세션도 "앱이 언제까지 막히는가"를 정하는
일이므로 그 질문을 하는 자리가 이미 있었던 셈이고, 초안은 그 옆에 새 진입점을 하나 더 판 것이다.

**사이클만 시트에서 설정을 끝내지 않고 제 화면으로 넘어간다.** 길이 하나가 아니라 시간표를
고르는 일이고, 2시간이 넘는 잠금을 거는 결정이라 좁은 시트가 아니라 제 화면에서 한다. 다른 두
세그먼트와 동작이 다른 것은 의도된 비대칭이다.

사이클 세그먼트에서는 타이머 전용 요소를 숨긴다 — 상단 `종료 시간` 줄과 하단 `선택한 시간까지
앱이 잠겨요` 안내다. 사이클은 여기서 만료 시각을 고르지 않으므로, 남겨 두면 세션과 무관한 시각이
이 세션의 종료 시간인 것처럼 읽힌다.

"스토어 포지셔닝 계약"이 이미 *"40dp 아이콘은 발견성을 감당하지 않는다, 신규 유입의 발견성은
스토어가 담당한다"* 고 적어 두었으므로 진입점을 합쳐도 포지셔닝 베팅은 깨지지 않는다.

**다만 기존 사용자는 새 기능이 생긴 것을 모른다.** 일회성 안내가 필요하고, 아직 없다.

## 차단 화면 컨텍스트 계약

집중 세션이 띄운 차단 화면은 지금이 어느 구간인지 말한다. 그러지 않으면 사용자는 세션 화면으로
돌아가야만 자기가 어디쯤인지 알 수 있다.

- 집중 중: `지금은 집중 시간이에요` + `N번째 집중이 M:SS 남았어요`
- **휴식 중: `지금은 휴식 시간이에요` + `휴식이 M:SS 남았어요. 세션이 끝날 때까지 앱은 계속 막혀 있어요.`**

**휴식 문구가 이 기능에서 가장 중요한 카피다.** "쉬는 중인데 왜 안 열리지"가 첫 반응이고, 그 순간이
휴식에도 차단이 유지된다는 계약을 다시 말해야 하는 유일한 자리다.

세션이 없거나 이미 끝났으면 아무것도 붙이지 않는다 — 그때 차단은 다른 잠금이 만든 것이고, 집중
세션 문구를 얹으면 거짓말이 된다.

세션 자체가 아니라 화면이 쓸 값만 넘기는 `PomodoroBlockContextSource` 이음매를 둔다. 차단 화면은
공개 표면이고 세션은 아니다 — `ParentModeBlockReasonSource` 와 같은 이유다.

### 구현 중 발견한 버그

`LockScreenMode` 에 `Pomodoro` 가 없어서 `toLockScreenMode()` 가 `pomodoro` 를 `else ->
ManualKeep` 으로 떨어뜨리고 있었다. 차단은 정상이었지만 **화면에 도달하는 출처가 조용히 바뀌어**
세션 문구가 통째로 사라졌다. `AnalyticsBlockSource` 에 값을 더할 때 이 enum 도 함께 봐야 한다.

### 실기기 검증 미완

이 항목의 실기기 렌더링은 아직 확인하지 못했다. 검증 도중 `adb shell am force-stop` 을 썼는데
Samsung 이 그 앱의 접근성 서비스 등록을 목록에서 빼버려 차단 자체가 멈췄다. 설정 UI 에서 dev 앱
접근성을 다시 켠 뒤 재확인해야 한다. (prod 앱 등록은 영향받지 않았다.)

## 휴식 중 차단 계약

**경쟁 앱 리서치로 뒤집어 본 항목이다.** 초안은 "휴식에도 무조건 차단"을 핵심 계약으로 못 박았는데,
이 카테고리의 기본 동작은 반대다.

| 앱 | 휴식 중 |
| --- | --- |
| AppBlock | *"releases them only during breaks"* — 열림 |
| BlockSite Pomodoro | 휴식엔 열림, 계속 차단은 `strict blocking` 옵션 |
| Focus (Mac) | 기본 열림, 휴식 소진 후 계속 차단은 옵션 |

### 결정 — 옵션으로 두되 기본은 켜짐

시장을 그대로 따르지 않는다. **이 앱을 고른 이유가 차단이기 때문이다.** 뽀모도로 전용 앱 사용자는
휴식에 SNS를 보러 가지만, 이 앱 사용자는 그걸 막으려고 왔다. 기본을 뒤집으면 제품 정체성이 바뀐다.

동시에 카테고리에서 넘어온 사용자에게는 관례대로 쓸 길을 준다. 설정 화면의
`휴식 중에도 계속 막기` 토글이 그 자리다.

### 구현 계약

세션은 사이클 전체 길이의 타이머 잠금 하나를 만들고, 세션이 도는 동안 그 잠금은 세션의 것이다
(세션 시작이 이미 활성 잠금을 거부하므로 겹칠 수 없다). 그래서 휴식 차단을 끄면 **세션뿐 아니라
그 잠금까지 함께 물러나야 한다.** 세션만 물러나면 `isLockTime` 이 남아 결국 `timed_lock` 으로
계속 막히고, 설정이 아무 일도 하지 않는다.

물러나는 것은 세션이 만든 잠금뿐이다. **루틴·목표 잠금·부모 모드·즉시 차단은 영향받지 않는다** —
세션이 만든 것이 아니고, 사용자가 따로 건 약속이다.

정책은 두 질문을 분리한다.

- `PomodoroPolicy.isActive(...)` — 세션이 살아 있는가 (잠금이 누구 것인지 판단)
- `PomodoroPolicy.blocksNow(..., blockDuringBreaks)` — 지금 막아야 하는가

## 빠른 시작 계약

이 카테고리의 필수 요건은 **"1–2탭 안에 세션 시작"**이다. 진입점을 타이머 시트로 합친 직후 경로는
`아이콘 → 사이클 세그먼트 → 설정하기 → 집중 시작` 으로 **4탭 + 세그먼트를 발견해야** 했다. 합친
방향은 옳았지만 결과적으로 시작을 더 어렵게 만들었다.

- **마지막으로 고른 사이클을 기억한다.** 세션이 끝나도 남는다.
- 시트의 사이클 패널이 그 사이클과 **총 잠금 시간**을 바로 보여주고, CTA 가 `집중 시작` 이다.
  세부 편집은 `변경` 링크로 빠진다.
- 전에 써 본 사용자는 시트가 **사이클 세그먼트로 열린다** → `아이콘 → 집중 시작` 2탭.
- 시트에서 시작하면 설정 화면을 거치지 않는다(`PomodoroRoute(autoStart = true)`).
  지난 세션의 완료 화면이 남아 있으면 먼저 치우고 시작한다 — 그러지 않으면 "집중 시작"을 눌렀는데
  지난 결과가 뜬다.

## 플로우 계약

기능이 도는 것과 플로우가 이어지는 것은 다르다. 실기기에서 처음부터 끝까지 따라가며 잡은 것들이다.

### 세션 전체 길이를 반드시 말한다

**가장 중요한 항목이다.** 사용자가 고르는 것은 "집중 50분"이지만 실제로 예약되는 잠금은
`4×50 + 3×10 + 20 = 250분`, 즉 **4시간 10분**이다. 이 숫자를 말하지 않으면 사용자는 자기가
얼마를 거는지 모르고 시작한다.

`DESIGN.md` 의 브랜드 신뢰 신호가 "predictable lock state, clear remaining time"인데, 그것을
정면으로 어기는 상태였다. 시작 버튼 **바로 위**, 즉 커밋이 일어나는 자리에서
`집중 4번 · 총 N시간 M분 동안 막혀요` 를 보여주고 선택·스테퍼 변경에 따라 즉시 갱신한다.

### 막다른 길을 만들지 않는다

차단 앱이 0개면 시작 버튼이 비활성이었고, **왜 못 누르는지도 어디서 고치는지도 없었다.**
이제 이유를 문장으로 말하고 `차단 앱 고르기` 버튼을 그 자리에 둔다.

앱 선택은 홈의 바텀시트가 소유하고 있어 다른 화면에서 직접 띄울 수 없다. `HomeRoute` 에
`openAppSelection` 플래그를 두어 홈으로 돌아가면서 시트까지 열어 준다 — 홈에 내려놓고 끝내면
사용자는 왜 돌아왔는지 모른 채 홈을 다시 훑어야 한다.

`막을 대상` 줄도 눌러서 같은 곳으로 간다. 읽기만 되는 줄이면 대상을 바꾸려고 홈까지 나갔다 와야
한다.

### 끝난 방식에 맞는 문장을 쓴다

시간표를 끝까지 돈 세션과 사용자가 5초 만에 끊은 세션은 다른 이야기다.

| 상황 | 제목 | 부제 |
| --- | --- | --- |
| 끝까지 완주 | `세션을 마쳤어요` | `오늘 기록에 남았어요` |
| 사용자가 종료 | `세션을 끝냈어요` | 위와 같음 |
| 집중 0회 | (위 규칙대로) | `잃는 건 없어요. 언제든 다시 시작할 수 있어요.` |

`docs/BLOCK_SCREEN_COPY_HIERARCHY.md` 의 코칭 톤과 같은 방향이다. 아무것도 못 한 세션에
"완료한 0회는 기록에 남아요"라고 말하면 문장도 성립하지 않고, 못 했다는 사실만 남는다.

## 상태/도메인 계약

구현 이름은 code lane이 확정하되, 정책 테스트는 아래 개념을 보존해야 한다.

| 필드 | 의미 | 주의 |
| --- | --- | --- |
| `cycle` | 집중/짧은 휴식/긴 휴식 길이 + `kind`(`25_5`/`50_10`/`custom`) | 길이는 값으로 저장한다. analytics 는 `kind` enum 과 `focus_minutes_bucket` 만. 분 단위 원문 전송 금지 |
| `phase` | `focus`, `short_break`, `long_break` | 휴식도 세션의 일부이며 차단 활성 구간이다 |
| `cycleIndex` | 현재 사이클 번호(1-based) | analytics는 bucket으로만 |
| `phaseDeadline` | 현재 페이즈 만료 `Instant` | `docs/MANUAL_TIMER_LOCK_DEADLINE_CONTRACT.md`와 같은 ISO-8601 `Instant` 규약을 따른다. `LocalDateTime` 저장 금지 |
| `sessionStartedAt` | 세션 시작 `Instant` | raw 값은 analytics 금지. 경과 시간 bucket만 |
| `completedFocusCount` | 완료한 집중 페이즈 수 | 휴식은 세지 않는다 |
| `status` | `active`, `completed`, `ended_early` | 종료 사유를 구분해서 기록한다 |

`phaseDeadline`을 `Instant`로 고정하는 이유는 기존 계약과 같다 — timezone이 바뀌어도 같은 실제 시각에 만료되어야 한다.

### 차단 판단 정책

정책 helper는 Android framework 없이 JVM 테스트 가능한 순수 함수로 먼저 만든다. `ManualLockTimePolicy`가 선례다.

**핵심 계약 — 휴식 중에 차단을 풀지 않는다.**

휴식 5분에 차단을 해제하면 `KeepAccessibilityService`의 차단 판정에 "의도적 비차단" 상태가 하나 생기고, 긴급해제·부모 모드·목표 잠금·루틴과의 우선순위를 전부 다시 정의해야 한다. #1177급 작업이 다시 발생한다. 그보다 큰 문제는 제품 쪽이다 — 사용자가 앱에서 이탈하는 지점이 정확히 그 휴식 구간이다.

대신 **휴식 화면을 앱 안에 둔다.** 앱 자체가 휴식이 된다. 차단 상태는 세션 내내 연속이라 상태 기계가 늘지 않고, 휴식 시간이 그대로 인앱 체류로 바뀐다.

필수 정책 케이스:

1. `focus` 진행 중 — 선택 앱 차단.
2. `short_break` / `long_break` 진행 중 — **차단 유지.** 이 케이스가 깨지면 계약 위반이다.
3. 세션 완료 또는 사용자 종료 이후 — 차단 없음.
4. 앱 종료 후 재실행 — 벽시계 기준으로 현재 페이즈를 재계산한다. 여러 페이즈가 지났으면 지난 집중 페이즈만 `completedFocusCount`에 반영하고 휴식은 소비된 것으로 본다.
5. timezone 변경 — `Instant` 기준이므로 만료 시각이 이동하지 않는다.
6. 부모 모드 활성 중 — 뽀모도로 세션을 시작할 수 없다. 부모 모드가 최상위 계약이다.
7. 루틴/목표 잠금이 이미 차단 중인 앱 — 뽀모도로 세션이 기존 차단을 **약화시키지 않는다.** 세션이 끝나도 루틴/목표 잠금 차단은 그대로 유지된다.
8. 긴급해제 — 뽀모도로 차단은 열 수 있다. 자기통제 잠금이므로 #1177에서 부모 모드를 막은 것과 반대 방향이다.

`block_source` 우선순위 확정은 code lane 몫이되, 6·7번은 정책 테스트로 고정한다.

### Analytics block source

`AnalyticsBlockSource`에 `pomodoro`를 추가한다. 기존 5종(`manual_keep`, `timed_lock`, `routine`, `goal_lock`, `parent_mode`)의 의미는 바꾸지 않는다. 뽀모도로 세션 중 차단은 `timed_lock`으로 합산하지 않는다 — 합치면 이 베팅의 성과를 기존 타이머와 분리할 수 없다.

## UX / 카피 계약

### 진입점

**홈 상단에 카드를 새로 추가하지 않는다.** `docs/HOME_STATUS_CTA_STRUCTURE.md`가 superseded되면서 남긴 경고 그대로다 — 상단에 카드를 더 붙이면 #1151(큰 글꼴에서 잠금 스위치가 스크롤 밖으로 밀림)이 악화된다. 카드 한 장 선택은 `HomeCardArbiter`가 소유하고 있고, 여기에 `HomeCard` variant를 늘리는 것도 MVP 범위 밖이다.

MVP 진입점은 홈의 기존 보조 진입점 계열(타이머 설정과 같은 위계, 40dp)과 메뉴 두 곳으로 한정한다. 세션 진행 중 상태 표시는 새 카드가 아니라 기존 active lock status 표면을 재사용한다.

**이 진입점이 발견성을 감당하지 않는다는 점을 명시해 둔다.** 40dp 아이콘은 이미 앱을 쓰는 사람에게만 보인다. 뽀모도로로 유입된 신규 사용자의 발견성은 위 "스토어 포지셔닝 계약"이 담당한다. 홈 면적을 더 쪼개서 이 문제를 풀려는 시도는 #1151을 악화시키고, 그렇게 해도 신규 유입에는 닿지 않는다.

세션 진행 중에는 홈이 아니라 세션 화면이 사용자가 있는 곳이며, 진행 상태는 세션 진행 알림이 앱 밖에서 이어받는다.

### 톤

`docs/BLOCK_SCREEN_COPY_HIERARCHY.md`(#464)의 코칭 톤을 그대로 따른다. 이 기능에서 특히 금지할 것:

- 휴식을 건너뛰라고 부추기는 문구.
- 중단·종료를 실패로 그리는 문구("포기하시겠어요?", "아쉽네요" 류).
- 연속 기록 단절을 경고하는 문구.
- 오늘 사이클 수가 0인 상태를 부정적으로 묘사하는 문구.

`docs/RETENTION_DIAGNOSIS_2026_08.md` 4장이 완주 압박의 근거를 뒤집었다는 점을 기억한다. 완주율을 올리는 카피가 `app_remove`를 올리면 순손실이다.

### 런타임 증적 (실기기 SM-G991N, 2026-08-31)

`:app:testDevDebugUnitTest` / `:app:lintDevDebug` / `:app:assembleDevDebug` 성공.
로케일 parity 뽀모도로 위반 0건.

- 메뉴 첫 행 `집중 세션 시작` → 설정 화면. 홈 시트 진입점과 같은 화면이다.
- 세션 시작 → `pomodoro_started_at` 08:16:21Z, `lock_time` 10:26:21Z. 정확히 2시간 10분
  (집중 25×4 + 짧은 휴식 5×3 + 긴 휴식 15). 뽀모도로가 별도 잠금을 만들지 않고 타이머 잠금
  하나로 합류한다는 계약이 저장값으로 확인된다.
- `pomodoro_phase_deadline` 08:41:21Z — 첫 집중 25분.
- 진행 화면이 원형 링 안에 `24:56` / `25분 중 남은 시간`, 아래에 `1번째 집중 · 4번 중`.
- 세션 종료 → `pomodoro_status=ended_early`, `lock_time` 키 자체가 사라진다.
- 접근성 서비스 등록(prod + dev) 무손상.

기기 검증에서 잡아 고친 것:

1. 집중 0회 종료 확인 문구가 `"완료한 0회는 기록에 남아요"`로 성립하지 않았다 → 0회 전용 문구.
2. 세션 중 홈이 `"StopIt is off"` 라고 말했다 → 홈 상태를 세션 인지형으로.
3. `LockScreenMode` 에 `Pomodoro` 가 없어 차단 화면이 조용히 `manual_keep` 으로 떨어졌다.
4. 스플래시가 세션 중에 잠금 화면으로 보내 세션을 끝낼 수 없었다 → `MoveToPomodoro`.
5. 설정 화면에 스크롤이 없어 커스텀 카드를 펴면 `집중 시작` 이 화면 밖으로 밀렸다.
